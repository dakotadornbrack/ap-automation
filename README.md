# AP Invoice Automation

Takes messy invoice exports, cleans and validates them, loads them into Postgres, and flags the two things an AP team most needs to catch before cutting checks: **invoices about to be paid twice**, and **invoices already past due**.

> **All data in this repository is synthetic.** It is generated by `python -m ap.generate` from a fixed seed. No real vendor, invoice, or payment information appears anywhere in this project, and none should ever be committed to it.

---

## The problem

Invoice data arriving from scanning vendors, supplier portals, and email is inconsistent in ways that break naive matching:

| What arrives | Why it matters |
|---|---|
| `ACME Corp.`, `Acme Corporation`, `  acme corp ` | Three vendor records for one payee; duplicate checks scoped per-vendor miss the overlap |
| `03/15/2024`, `15-Mar-2024`, `20240315` | A single date parser silently mangles or drops rows |
| `$1,234.56`, `(450.00)`, `450.00CR` | Credits parsed as positives inflate the payables balance |
| `INV-0042` and `INV42` | The same invoice submitted twice, invisible to an exact-string check |
| Missing due dates | No due date means no aging, so the invoice never appears as late |
| `settled`, `cancelled`, `disputed` | Status vocabularies differ per source system; an unmapped value must not silently become `open` |

The pipeline normalizes all of it, then runs a rule engine over the result.

## What it does

```
CSV → clean & validate (Python) → Postgres → rule engine (SQL) → dashboard
                    ↓
              quarantine.csv
```

1. **Clean.** Vendor names, dates, and amounts are normalized by small pure functions. Money is parsed to `Decimal` and stays `Decimal` end to end.
2. **Quarantine.** Rows that cannot be trusted are written to `data/quarantine/` with a `reject_reason` column, keeping their original values so a clerk can fix and resubmit. Nothing is silently dropped.
3. **Load.** Idempotent. Re-running the same file is a no-op, tracked by file hash — an AP pipeline that double-loads is indistinguishable from one that causes double payments.
4. **Detect.** Ten rules write findings to an `exceptions` table.
5. **Report.** A dashboard reads views only, never the base tables.

## Detection logic

Each rule writes one row per finding into `exceptions`, tagged with a `rule_code` and severity. All rules are `INSERT ... ON CONFLICT DO NOTHING`, so the engine is safe to re-run.

**Duplicates**

- `DUP_EXACT` — same vendor and invoice number after stripping punctuation and leading zeros, so `INV-0042` and `INV42` collide. A database constraint blocks byte-identical duplicates at load; this catches the ones that differ only in formatting.
- `DUP_NEAR` — same vendor, same amount, invoice dates within 5 days, different invoice number. This is the classic double-pay: a supplier re-sends an unpaid invoice under a new number.
- `DUP_FUZZY_VEND` — same amount within 15 days across two vendor records whose normalized names have a trigram similarity of 0.55 or higher. Catches the case where a typo in the vendor master created a second payee.

**Aging and controls**

- `OVERDUE_30` / `_60` / `_90` — one finding per invoice at its worst tier, not three as it ages.
- `AMT_THRESHOLD` — over the 10,000 approval limit.
- `MISSING_GL`, `FUTURE_DATE`, `LINE_MISMATCH` — data-quality controls. `LINE_MISMATCH` allows one cent of tolerance to absorb legitimate rounding on unit-price math.

## Design decisions

**Duplicates are findings, not rejects.** The cleaner deduplicates within a file on the *raw* invoice number, not the normalized one. A row repeated byte-for-byte is a data-entry error and goes to quarantine; `INV-0042` arriving next to `INV42` is a business finding, so both are loaded and reported as a pair. Normalizing at that step would silently swallow exactly the duplicates the project exists to surface.

**Money is `Decimal`, never `float`.** A tenth of a cent of drift is a real defect in a payables system, and it compounds across aggregation.

**Date parsing is an explicit format list, with no fuzzy fallback.** Guessing at `03/04/2024` is how a ledger ends up off by a month. Unparseable dates are quarantined rather than inferred. The month-first reading of ambiguous dates is a documented choice, asserted in the tests so any change to it is deliberate.

**An unrecognized status is rejected, not defaulted.** Quietly mapping an unknown status onto `open` would add a possibly-settled invoice to the payables balance. Known synonyms (`settled`, `cancelled`, `disputed`) are mapped explicitly; anything else is quarantined. A test asserts every value the cleaner can emit satisfies the schema's CHECK constraint, so drift between the two shows up as a readable reject reason rather than an integrity error at load time.

**Duplicate rules ignore only voided invoices, not paid ones.** A duplicate of an already-paid invoice is precisely the double-payment that matters; excluding paid invoices would hide the finding you most want.

**The generated data is calibrated, and that calibration is itself a finding.** The first version drew invoice amounts uniformly, which put 67% of the ledger over the approval threshold, and never marked anything paid, which left 40% of invoices in the 90+ bucket. Both made the rules look broken. Amounts are now log-normal — right-skewed, like real invoice values — and invoices are marked paid with a probability that rises with age. The result is a normal aging curve and a threshold that flags about 6% of open invoices.

**The invoice-number normalizer exists twice**, in Python for cleaning and in SQL for the duplicate joins. Two copies of a rule drift apart silently, so `tests/test_parity.py` asserts the two implementations agree on a corpus of awkward inputs.

## Testing

```bash
make test      # pytest with coverage
make lint      # ruff
```

CI runs lint, unit tests, and a full end-to-end pipeline against a real Postgres service container — the SQL rules are exercised, not mocked. It then asserts that the rule engine actually produced findings, that no invoice line is orphaned, that the aging buckets sum to the headline KPI, and that re-ingesting an already-loaded file is a no-op. Without those assertions the pipeline could load nothing at all and a green test run would still say everything is fine.

## Limitations

Worth being straight about, since these are the first things a reviewer should ask:

- **The similarity threshold is not tuned.** 0.55 was chosen to work on generated data. Setting it honestly requires a labeled sample of real vendor pairs and a precision/recall tradeoff made with the AP team — too low floods the queue with false positives, too high misses real duplicates.
- **No three-way match.** Real AP matches invoice to purchase order to goods receipt. This only sees invoices, so it cannot catch billing for goods never received.
- **Exceptions are never auto-resolved.** The `resolved_at` column exists and the views respect it, but nothing sets it. A production version needs a review workflow.
- **Single currency in practice.** The schema carries a currency column, but no FX conversion, so cross-currency totals would be wrong.
- **Duplicate detection is pairwise.** Three copies of an invoice produce three pair findings rather than one cluster of three.

```

sql/002_views.sql      aging and reporting views
sql/003_rules.sql      the rule engine
src/ap/generate.py     synthetic dirty data (stdlib only)
src/ap/clean.py        parsing, normalization, validation
src/ap/load.py         idempotent loader
src/ap/db.py           connection and migrations
src/ap/cli.py          migrate / ingest / rules / report
dashboard/app.py       Streamlit dashboard
scripts/               CI smoke assertions
tests/test_clean.py    parsing, normalization, validation
tests/test_load.py     row building at the pandas/psycopg2 boundary
tests/test_generate.py the generated data actually exercises every rule
tests/test_parity.py   Python and SQL normalizers agree
```
